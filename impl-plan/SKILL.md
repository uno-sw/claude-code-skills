# 実装計画書の作成

既存のドキュメント（要件定義書、企画書、仕様書など）を読み込み、アジャイル方式の実装計画書を Markdown ファイルとして出力する。

## 手順

### 1. 入力ドキュメントの確認

ユーザーに以下を確認する:

- **参照するドキュメント**: パスを聞いて全て読み込む。複数可。
- **出力先**: 計画書を保存するパスを提案し、確認を取る。プロジェクト構成を見て適切な場所を判断する（例: `docs/implementation-plan.md`）。

### 2. ドキュメントの分析

読み込んだドキュメントから以下を抽出する:

- プロダクトの目的・ゴール
- 機能要件の一覧
- 非機能要件（あれば）
- 技術的な制約・前提条件
- 既存システムとの連携（あれば）

### 3. イテレーション設計

以下の原則に従ってイテレーションを設計する:

#### 核心原則: 動くものを積み重ねる

- **ウォーターフォール禁止**: 「まず全体の基盤を作り、次に全機能を載せる」ではなく、「小さく動くものを作り、機能を足していく」方式で計画する。
- **各イテレーション終了時に視覚的に確認できる成果物があること**: これは必須条件。画面、出力、動作するUIなど、目で見て「動いている」と分かるものがあること。
- **成果物は確認用の一時的なものでもよい**: 最終形でなくてよい。ハードコードされた値を表示するだけ、モックデータで動くだけ、でも構わない。後のイテレーションで本物に差し替えればよい。
- **機能ごとの縦割りで進める**: レイヤーごと（横割り）ではなく、機能ごと（縦割り）に実装する。例えば「まずDB層を全部作り、次にAPI層を全部作り…」ではなく、「機能Aに必要なDB・API・UIをまとめて作る」方式で進める。
- **イテレーションはなるべく細分化する**: 大きな機能は複数イテレーションに分割する。「1イテレーション = 1つの確認可能な進捗」を目指す。
- **コンポーネントの用意は実際に必要になるまで遅らせる**: 「将来使うから先に作っておく」は禁止。管理クラス・基盤システム・抽象化レイヤーなどは、それを使う機能を実装するイテレーションで初めて導入する。例: 画面遷移管理は複数画面が実際に必要になるイテレーションで作る。サウンドマネージャーはサウンドを組み込むイテレーションで作る。あるイテレーションのタスクに「〇〇の骨格を用意」「〇〇管理の基礎」のような項目が含まれていたら、それは本当にそのイテレーションで使うのかを再確認する。
- **すべての完了条件は機械検証可能にする**: 「目で見て確認」のみで完了とする項目を作らない。視覚成果物がある場合でも、必ずエージェントが exit code・ログ・スナップショット・HTTP レスポンス・画像のマルチモーダル直接確認 等で pass/fail を判定できる手段を併設する。これがないとエージェントは自走できない。

#### 設計の進め方

1. 機能要件をユーザーストーリーまたは機能単位に分解する
2. 依存関係を整理する
3. 以下の順でイテレーションを組み立てる:
   - **最初のイテレーション**: 最小限の動作する画面 or 出力。技術スタック確認も兼ねる
   - **以降のイテレーション**: 機能を1つずつ追加し、毎回「見て確認できる」状態にする
   - **後半のイテレーション**: 仕上げ（エラー処理、バリデーション、UI調整など）
4. 各イテレーションに **テスト項目** を「手動確認項目」と「自動検証項目」に分けて記載する:
   - **手動確認項目**: 人間が画面や出力を目で見て確認するもの。ユーザー操作の手順（「〇〇画面で△△を入力し、□□が表示されることを確認」など）と期待される表示を明記する
   - **自動検証項目**（必須・1つ以上）: エージェントが自走で pass/fail を判定できる項目。各項目に **実行コマンド** と **判定基準**（exit code 0 / 特定文字列の存在 / ファイル生成 / スナップショット一致 / 画像のマルチモーダル確認結果 など）を必ず明記する

### 4. テストハーネス設計（自走対応）

エージェントが人間の介入なしに各イテレーション完了を判定できる検証基盤を計画書に含める。具体ツール（Playwright/pytest/Vitest 等）には依存せず、対象プロジェクトに合わせて以下の観点を計画書に書き起こす:

- **統一エントリポイント**: `setup` / `run` / `verify` の3コマンドだけで全検証が走るようにする。`verify` の **exit 0 = そのイテレーション完了** と定義する
- **判定の一意性**: すべての検証は exit code、または grep 可能な構造化ログ（JSON Lines 推奨）で pass/fail が機械的に決まること
- **再現性の確保**: 乱数シード固定、時刻のモック、外部依存（ネットワーク・DB・LLM 等）のスタブ化方針
- **観測手段**: 標準出力・構造化ログ・スクリーンショット/スナップショット・HTTP応答・画像のマルチモーダル直接確認 のうち何を採用するか
- **UI/視覚成果物の機械化**: 画面確認は以下のいずれか1つ以上を必ず計画する
  - ヘッドレスブラウザ等でスクリーンショットを固定パスに出力 → **エージェントが Read ツールで画像を直接マルチモーダル確認** し「期待される表示状態」と一致するかを判定（ゴールデンが未整備でも初回から運用可能）
  - スクリーンショット + ゴールデン画像比較（pixelmatch 等）
  - DOM / テキスト / アクセシビリティツリーへのアサーション
  - 動画/GIF キャプチャをフレーム分解してマルチモーダル確認
- **マルチモーダル確認の判定基準明記**: 「〇〇ボタンが赤色で中央に表示」「エラーメッセージが日本語で表示」など、何が映っていれば pass かを計画書に書く
- **観測物の保存先**: ログ・スクリーンショット・スナップショットを固定パスに揃え、失敗時に何を見れば原因がわかるかを明記する

### 5. 計画書の出力

[template.md](template.md) のテンプレートに従って計画書を作成し、指定パスに保存する。

### 6. 確認

出力後、ユーザーに以下を伝える:

- 計画書の保存先パス
- 全体のイテレーション数と概要
